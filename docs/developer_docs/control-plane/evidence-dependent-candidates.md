# Evidence-dependent Planner candidates

ASAPPlanner keeps constructible summary candidates in `PlanSpace` when a proof or comparable cost is missing. The backend's selection trace reports each candidate's `accuracy_status`, symbolic `guarantee`, `runtime_support_status`, `estimated_cost_status`, and `decision_reason`. A candidate in the trace is not a deployable physical plan. `KeepPreAsap` remains the exact fallback.

`BackendLocalPhysicalInputs.accuracy_evidence` (keyed by registered query text) and `CompileAndPublishPhysicalPlanRequest.accuracy_evidence` (keyed by query ID) supply optional `ScopedAccuracyEvidence`. Each record must name the exact query text, full `DataWorkload`, data snapshot ID, source, observation time, and validity window. Discovery without a workload quote must provide `data_snapshot_id`; a quote and explicit ID must agree. A record for another query, workload, or snapshot, or an expired, future-dated, incomplete, or invalid record is rejected before Planner selection. Omitted facts remain unknown.

The record can carry enforced bounds for individual serialized `QueryExpr` operands (`quantile_operand_domains`), non-negative values, input row count, Hydra shared-grid collision and failure bounds, and TopK selected/excluded intervals and failure probability. Quantile bounds must describe a source contract, not observed sample extrema. A TopK interval is accepted only when all three bounds are present and the selected lower bound exceeds the excluded upper bound. Existing legacy `topk_evidence` remains supported for compatibility; new evidence producers should use the scoped record.

The backend permits Planner's qualitative ranking when numeric cost is unavailable, but the workload quote and physical compiler still decide deployment. The physical compiler rejects a selected summary readout with an unknown `ResultGuarantee` and validates the executable DAG against supported operators and runtime policy. Current ERP v1 measurements report observed error without a calibrated failure probability, so they cannot certify an `(ε,δ)` guarantee. HLL relative standard error alone likewise does not certify a tail probability. These cases stay visible in explain output and use exact execution unless a future proof model establishes the missing guarantee.
