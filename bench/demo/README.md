# Live demo and comparison tooling

Scripts that run the ASAP data plane next to VictoriaMetrics single-node
(and Prometheus as the exact reference) on the same Remote Write feed and
the same queries, and show both on Grafana. Code and configuration only: no
run outputs are kept here.

| Directory | What it holds |
|---|---|
| `run_live_demo.sh` | The live Grafana demo: feeders, the three engines, proxies, exporters, a watchdog and the query load. |
| `run_vm_demo.sh` | The batch comparison: prepare, run the arms one after another on one feed, report. |
| `fetch_binaries.sh`, `build.sh` | Pinned third-party binaries (sha256-checked) and the builds of the feeder, ASAPQuery and this repository. |
| `harness/` | `prepare.py` (scaled manifest, feeder table, the Planner's plan through `control_plane`), `run.py` (arms), `report.py`, `accuracy_vs_vm.py`, `cgroup_limits.sh`. See `harness/README.md`. |
| `live/` | The live demo's helpers: `proxy.py` (logging pass-through for Grafana), `query_load.py` (simulated users), `accuracy.py` and `compare.py` (answers against the exact reference), exporters for ingestion, limits, planner and experiment facts, and the run sequences (`demo_sequence*.sh`, `chain_*.sh`). |
| `monitoring/` | Prometheus and process-exporter configuration, Grafana provisioning and the dashboard generators (`grafana/make_*_dashboard.py`), screenshots (`screenshot.py`/`.sh`), Docker Compose or plain binaries (`run_binaries.sh`). |
| `workloads/` | Workload manifests (queries, labels, data facts) and their generators in `campaign/gen_*.py`. |
| `campaign/` | Multi-host campaign scripts (job queue, scale sweep, reruns, collection, summaries) and patches applied to the harness during the campaign. They expect the environment variables below on every host. |

## Setup

Everything runs from one working directory, `$ASAPQ_BENCH`. Use this
directory and put the checkouts the scripts build next to it:

```sh
export ASAPQ_BENCH=$(git rev-parse --show-toplevel)/bench/demo
export BIN_DIR=/path/to/bin            # pinned binaries and the built data_plane/control_plane
ln -s ../.. "$ASAPQ_BENCH/backend"     # this repository
git clone https://github.com/ProjectASAP/ASAPQuery "$ASAPQ_BENCH/ASAPQuery"   # paced_feeder
./fetch_binaries.sh                    # VictoriaMetrics, Prometheus, exporters, Grafana
./build.sh
```

| Variable | Used by | Meaning |
|---|---|---|
| `ASAPQ_BENCH` | all | the working directory above |
| `BIN_DIR` | all | binaries |
| `BENCH_ENV` | shell scripts | optional file sourced first (toolchain paths) |
| `BENCH_ROOT` | `build.sh`, `campaign/` | directory holding other checkouts and scratch files |
| `ASAP_PLANNER_DIR` | `harness/prepare.py` | an ASAPPlanner checkout (feature checks by commit) |
| `CAMPAIGN_DIR` | `campaign/` | the job queue's directory on each host |
| `BENCH_HOSTS`, `BUILD_HOST`, `REF_HOST`, `ENGINE_SSH`, `ENGINE_ADDR` | `campaign/` | host names as `ssh` resolves them (driver hosts, build host, reference replay host, engine host) |

## Live demo

```sh
SERIES=10000 ./run_live_demo.sh start   # plan once, start feeders/engines/proxies, wire up monitoring
./run_live_demo.sh status               # processes, ingestion, Grafana requests answered/refused
./run_live_demo.sh load on 8            # 8 simulated users querying every engine
./run_live_demo.sh compare              # ASAP and VictoriaMetrics against the exact reference
./run_live_demo.sh stop
```

`WORKLOAD` picks the manifest under `workloads/` (`dashboard-live` by
default, `asap-demo` for the presentation dashboard). `LIMITS=1` runs both
engines under the same enforced CPU, memory and disk limits
(`harness/cgroup_limits.sh`). Grafana listens on port 13000; the dashboards
are generated by `monitoring/grafana/make_live_dashboard.py` and
`make_demo_dashboard.py`. The header of `run_live_demo.sh` lists every
command, port and variable.

## Comparison

```sh
SERIES=1000 QUERY_PHASE_S=600 WORKLOADS="demo/dashboard-heavy" ./run_vm_demo.sh
```

For each workload this prepares the plan (timed as a one-time offline
cost), runs the arms (`asap`, `victoriametrics`, optionally `prometheus`)
on the same feed and query schedule, each on its own cpuset, and writes
`report.py` and `demo_table.py` tables with each arm's absolute CPU,
memory, disk, latency and accuracy. `harness/README.md` describes the arms,
flags and outputs.
